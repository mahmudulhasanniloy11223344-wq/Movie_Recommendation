Technical Deep Dive

How It Works

Every design decision was chosen for a measurable reason. Here's the theory behind each data structure.

⬡ Hash Table

O(1) movie lookup — constant time, every time

A hash function converts each movie ID into a memory address. No matter how many movies exist, the system retrieves any movie in exactly one step. We use two dictionaries: movie_registry (id → data) and user_ratings (id → score) to prevent double-counting votes.

Ratings use an aggregated model — only sum_rating and count are stored. The average is computed on demand, keeping updates at O(1).

⬡ FIFO Queue

Viewing history — first in, first out

The queue stores the last 5 movies you watched. When a 6th is added, the oldest entry is automatically removed from the front — the FIFO (First In, First Out) principle in action.

Implemented with collections.deque(maxlen=5). Appending to the back and removing from the front are both O(1). A regular list would cost O(n) for front removal because every element must shift left.

Enqueue & dequeue:O(1)

⬡ Graph + BFS

Genre graph — Breadth-First Search recommendations

Every movie is a node. Two movies share an edge if they have at least one genre in common. The graph uses an adjacency list (dict of lists) — memory-efficient for sparse graphs vs. a full adjacency matrix.

BFS starts from your watch history and explores genre-connected movies level by level — closest connections first. This ensures the most genre-relevant films appear at the top of your recommendations.

How the FIFO Queue works

Built with collections.deque(maxlen=5). When you watch a 6th movie, Python automatically removes the first entry (the oldest). Adding to the back and removing from the front are both O(1) — a list would cost O(n) because every item must shift left.
